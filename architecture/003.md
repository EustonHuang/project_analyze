# Agent 自身工作流追踪方案

## 目标

追踪对象从「某个具体 prompt 的经历」改为 **Agent 的系统级工作流**：无论用户输入什么 prompt，Agent 都必须经过哪些阶段、哪些路径是条件分支。渲染成流程图时，节点必须**按类型使用对应形状**——这是流程图的基本规范（条件用菱形只是其中一条，不是唯一需要形状的类型）。

## 核心修正

### 主线不再是 prompt，而是 Agent 会话生命周期
旧设计（architecture/001）把一次具体请求当作主线，导致流程图随 prompt 变化而变化。新设计的主线固定为：

1. 会话启动与上下文加载
2. 接收用户 query
3. 触发条件判断（rules / memories / skills / hooks）
4. 工具执行循环
5. 响应生成与输出

### 流程图节点按类型映射形状
workflow 中存在"条件"这类结构，而流程图中条件用菱形表示。菱形只是**形状映射表**中的一条；映射的目的，是让每一种节点类型都有正确形状，而非只有条件有形状、其余节点无形状。完整映射如下（渲染侧必须实现全套）：

- 起止（`entry` / `exit`）→ 圆角矩形（terminator）
- 处理（`step`）→ 矩形（process）
- 判断（`decision`，即条件）→ 菱形（decision）
- 输入/输出（`io`）→ 平行四边形（I/O）
- 并行（`parallel`）→ 虚线框容器
- 循环（`loop`）→ 圆角框容器 + 回边箭头

条件只是"判断"这一类节点的示例；`decision` 之外每种节点同样必须有自己的形状，缺一种都是不完整的流程图。

### 每个节点必须有来源
每个节点/边都要附带 `source`，证明该步骤不是猜测：

- `type`: `system_prompt` / `user_rule` / `workspace_rule` / `memory` / `skill_instruction` / `tool_spec` / `inferred`
- `path`: 规则文件路径、skill 路径、系统提示段落位置
- `quote`: 原文关键句或引用

## 追踪数据模型

一次追踪 `trace = { meta, phases[], conditions[], sources_map }`

### meta
- `kind`: `"agent_system_workflow"`
- `target`: Agent 类型/版本
- `created_at`

### phases[]
每个阶段 `phase = { id, name, kind, required, source, nodes[] }`

- `kind`: `sequence` / `conditional` / `loop` / `parallel`
- `required`: 该阶段是否无论 prompt 都执行
- `nodes[]`: 阶段内节点

### node
- `id`
- `kind`: `entry` / `decision` / `step` / `parallel` / `loop` / `io` / `exit`
- `label`: 人读标签
- `detail`: 具体做什么
- `source`: 来源对象
- `yes_branch` / `no_branch`: 仅 decision 节点
- `children[]`: 子节点

### conditions[]
显式登记所有决策条件，避免把 if 隐藏在 step 描述里：

```json
{
  "id": "C1",
  "question": "是否存在全局 user rules？",
  "kind": "rule_presence",
  "source": {
    "type": "system_prompt",
    "path": "always_applied_user_rules",
    "quote": "These are rules set by the user that you should follow if appropriate."
  }
}
```

## Agent 系统工作流（带条件分支）

### §1 会话启动与上下文加载

所有 prompt 的必经之路，按顺序执行：

1. `entry` 接收用户 query
2. `step` 加载系统指令与角色设定
3. `decision` 是否存在全局 user rules？
   - yes → `step` 加载并解析
   - no → 跳过
4. `decision` 是否存在项目 workspace rules？
   - yes → `step` 加载并解析
   - no → 跳过
5. `decision` 是否存在 memories？
   - yes → `step` 加载并匹配相关 memory
   - no → 跳过
6. `step` 加载用户环境信息（OS、shell、workspace、current_date 等）

来源：`always_applied_user_rules`、`always_applied_workspace_rules`、`<memories>`、`<user_info>`、`<additional_data>`。

### §2 用户 query 解析

1. `step` 解析用户输入文本/附件
2. `decision` 用户是否显式调用 skill？（如 `@command://agent-trace-view`、`<skill>` tag）
   - yes → 进入 §3-A 显式 skill 路径
   - no → 进入 §3-B 隐式 skill/规则判定路径

### §3-A 显式 skill 路径

1. `step` 定位 skill 定义（`.codebuddy/skills/<name>/SKILL.md`）
2. `step` 调用 `use_skill` 加载 skill 指令
3. `decision` skill 是否需要进一步调用工具？
   - yes → 进入 §4 工具执行循环
   - no → 进入 §5 响应生成

来源：`<available_skills>`、`agent_skills` 指令。

### §3-B 隐式 skill/规则判定路径

1. `step` 扫描可用 skill 列表
2. `decision` 是否有 skill 匹配用户意图？
   - yes → 回到 §3-A
   - no → 继续
3. `decision` 是否有 requestable user rules 需要加载？
   - yes → `step` 调用 `read_rules`
   - no → 继续
4. `decision` 是否有 requestable workspace rules 需要加载？
   - yes → `step` 调用 `read_rules`
   - no → 继续
5. `step` 进入通用问题求解流程

### §4 工具执行循环

这是一个 `loop` 阶段：

1. `step` 规划所需工具调用
2. `parallel` 并行执行独立工具调用
3. `io` 收集工具返回结果
4. `decision` 是否需要继续调用工具？
   - yes → 回到 §4-1
   - no → 退出循环

来源：`<tool_calling>` 系统指令。

### §5 响应生成与输出

1. `step` 综合工具结果、规则约束、记忆内容生成回复
2. `decision` 是否需要遵守响应语言规则？
   - yes → `step` 按 `<response_language>` 输出
   - no → 直接输出
3. `exit` 结束本轮

## 采集方式

不接运行时插桩，而是基于系统提示、规则文件、skill 定义做**结构化提取**：

1. 枚举系统提示中所有「必须/应当/条件」段落。
2. 把每个「如果……则……」转成一个 `decision` 节点。
3. 把每个无条件动作转成 `step` 节点。
4. 把「循环调用工具」表达为 `loop` 节点。
5. 把「skill 列表」与「agent_skills 触发条件」表达为条件分支。
6. 为每个节点填写 `source.path` 与 `source.quote`。

## 渲染要求

viewer 按节点 `kind` 渲染对应形状，形状映射为全套规范：

| kind | 流程图形状 | 说明 |
|------|-----------|------|
| `entry` / `exit` | 圆角矩形（terminator） | 起止 |
| `step` | 矩形（process） | 顺序处理 |
| `decision` | 菱形（decision） | 条件判断，出边标注 yes / no |
| `io` | 平行四边形（I/O） | 读写文件 / 调外部接口 |
| `parallel` | 虚线框容器 | 内含并行成员，无先后顺序 |
| `loop` | 圆角框容器 + 回边箭头 | 循环体，末节点回指首节点 |

边标注：`decision` 出边必须标注 `yes` / `no` 或条件表达式；其余边默认无标注。

控制条新增：

- `show_decisions_only`：只显示菱形节点，快速看清所有分支。
- `show_sources`：节点详情面板展开 `source.path` + `source.quote`。

## 交付物

1. 更新 `agent-trace` 采集侧：新增 `trace kind = agent_system_workflow`，生成带完整节点类型与 `source` 的 JSON。
2. 更新 `agent-trace-view` 渲染侧：按形状映射表渲染全部节点类型（圆角矩形/矩形/菱形/平行四边形/并行容器/循环容器）、边标注、source 详情。
3. 不改动现有 `trace kind = prompt_trace` 的兼容能力。

## 本期不做

- 动态运行时插桩采集（仍用结构化提取）。
- 多 Agent 协作/子 Agent spawn 的分布式追踪。
