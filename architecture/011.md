# architecture/011: 流程图应展示完整控制流，而非层级树

## 背景

上一版把流程图做成了「点击节点才展开下一步」的层级树，这不符合 trace 数据的实际语义。用户指出：

- **接收用户 query** 和 **注入 workspace rule** 是步骤 1 和步骤 2，它们是顺序执行的 **siblings**，不是 parent/child。
- **只有步骤 1 与步骤 1.1 这种真正的父子层级**才需要折叠/展开。
- `children` 字段在本项目 trace 里表示「下一步」，不是「子步骤」。
- P1、P2、P3、P4、P5 五个 phase 也是顺序执行的 siblings（阶段），不是父子。

## 问题分析

导致误判的原因是：我把通用树结构里的 `children` 语义直接套到了 workflow trace 上。实际上，本项目的 workflow 模型是：

- `phases`：顺序阶段（P1 → P2 → P3 → P4 → P5）。
- `phase.kind === "parallel"`：阶段内节点并行执行（如 P1 的 s1/s2/s3）。
- `phase.kind === "sequence"`：阶段内节点按 `children` 顺序执行（如 P2 的 n1→n2→n3→n4→n5）。
- `yes_branch/no_branch`：决策分支（如 n3 分 yes→n4、no→n5）。

因此流程图应当完整展示所有节点、顺序边和分支边，而不是默认只显示根节点。

## 方案

1. **默认展开全部节点和边**：流程图打开即显示完整控制流。
2. **保留缩放/平移/适应窗口**：节点密集时用户可以放大、拖拽、一键适应。
3. **移除对普通 `children` 的折叠逻辑**：不再把顺序下一步当作子步骤隐藏。
4. **保留可折叠语义（可选）**：如果未来 trace 出现真正的父子层级（如新增 `sub_steps` 字段），再恢复针对该字段的折叠；当前数据不适用。
5. **左侧面板标签保留**：「步骤」与「流程图」继续在左侧面板切换。
6. **点击节点仍联动详情**：点任意节点，中间来源详情与右侧文件查看器同步更新。

## 验收标准

1. 打开「流程图」标签，立刻看到全部步骤、连线、决策分支。
2. 不需要点击任何节点就能看清单个 phase 内的顺序关系（如 n1→n2→n3→n4→n5）。
3. 能看到 P1（并行）与 P2-P5（顺序）之间的整体流向。
4. 决策节点的 yes/no 分支清晰可见。
5. 点击节点仍能正确显示来源详情与文件定位。
