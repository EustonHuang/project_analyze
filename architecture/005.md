# architecture/005: project_analyze 项目本体追踪方案

## 目标

用 `agent-trace` skill 把 **architecture/003 描述的 Agent 工作流**实例化到 `project_analyze` 这个项目上，产出 `agent_traces/project_analyze_flow.json`：里面每个节点都不再引用抽象系统提示，而是锚定到本项目里的**具体文件 + 行号**。

003 已经定义了 agent 运行时要扫描/加载的类别（skills、rules、hooks、memories、工具等），005 的任务就是：**顺着这个流程走一遍，记录当前项目里这些类别对应的实际文件**。

## 背景

前序 001–004 有两条失败路径：
- 003/004 的 `agent_system_workflow.json` 是通用模板，虽然流程完整，但没有说明 `project_analyze` 这个特定项目长什么样。
- 004 改 viewer 时又为“中间空白”改 UI，改来改去 trace 内容还是与本项目无关。

005 把镜头对准项目本身，但仍以 003 的工作流为骨架——003 定义了要扫哪些**类别**，005 负责找到这些类别在 `project_analyze` 里的**具体实例**。

## 方法与数据流

003 的 Agent 工作流定义了 agent 会触碰的类别：

- **Rules**：全局 user rules、项目 workspace rules、requestable rules（需要 `read_rules`）。
- **Skills**：available skills（列表）、被 `use_skill` 调用的 skill（如 agent-trace 自身）。
- **Hooks**：`settings.json` 里的 hooks 驱动的 `turn_gate.py`。
- **Memories**：会话中注入的记忆（本项目当前有记忆记录）。
- **受管记录目录**：agent_traces / history / architecture / questions / improvements / custom（agent 写入的地方）。
- **工具循环**：validate.py、server.py 等具体脚本。

`agent-trace` 采集 `project_analyze` 时，就是**按 003 流程的每个步骤，去定位当前项目中该步骤实际对应的文件或目录**，并把结果写进 `agent_traces/project_analyze_flow.json`。

```
003 Agent 工作流
        │
        ▼
对 project_analyze 实例化
        │
        ├── 加载系统指令与角色设定 → 指向 system_prompt 改为指向本项目 settings.json hooks
        ├── 是否存在 user rules? → 指向 .codebuddy/rules/ 下具体 RULE.mdc + 行号
        ├── 扫描可用 skill 列表 → 指向 .codebuddy/skills/ 下每个 SKILL.md + 行号
        ├── 调用 use_skill → 指向被调用 skill 的 SKILL.md + 行号
        ├── 工具执行循环 → 指向 validate.py / server.py 等 + 行号
        └── 受管记录更新 → 指向 append_history.py + 行号
        │
        ▼
validate.py 校验（所有 source 指向项目内部文件 + 行号）
        │
        ▼
agent_traces/project_analyze_flow.json
        │
        ▼
agent-trace-view 渲染
```

## 节点来源原则

每个节点 source 必须满足：

- **Rules 相关节点**：指向 `.codebuddy/rules/` 下具体 RULE.mdc 文件 + 行号 + 原文 quote。
- **Skills 相关节点**：指向 `.codebuddy/skills/<name>/SKILL.md` + 行号 + 原文 quote。
- **Hooks / 守门相关节点**：指向 `.codebuddy/settings.json` 的 hooks 配置，以及 `.plan-standard/scripts/turn_gate.py` + 行号。
- **工具 / 脚本节点**：指向 `.codebuddy/skills/agent-trace/scripts/validate.py`、`.codebuddy/skills/agent-trace-view/server/server.py` 等 + 行号。
- **受管记录更新节点**：指向 `.plan-standard/scripts/append_history.py` + 行号。

禁止再引用系统提示原文或运行时变量（如模型名）。如果某一步在当前项目找不到具体文件，则放入 `assumptions[]`，不作为事实节点。

## Viewer 交互要求

沿用 004 三栏布局，并补齐缺口：

1. **节点 ID 可见**：左侧每行显示 `n4` 等 ID，分支目标一眼定位。
2. **双模式切换**：Anatomy/List 模式 与 Flowchart 模式互切，URL 保留 `?mode=flowchart`。
3. **真正展开/折叠**：phase header 可折叠；Flowchart 模式下子图可折叠。

## 验收标准

1. `agent_traces/project_analyze_flow.json` 由 agent-trace 实际产出，不是手填；每个节点 source 指向项目内部文件 + 行号。
2. 节点覆盖 003 流程中的类别（rules/skills/hooks/tools/managed dirs），且每个都锚定到 `project_analyze` 的具体文件。
3. viewer 打开后能看到：项目有哪些 skill/rule、守门脚本是谁、trace 数据从哪来到哪去；每个节点带 ID。
4. 支持双模式切换与 phase 展开折叠。
5. `validate.py` 通过。

## 交付物

1. `architecture/005.md`（本文件）。
2. 实际产出 `agent_traces/project_analyze_flow.json`。
3. 更新 `agent-trace/SKILL.md`：把「trace 项目自身」的步骤加进 skill 指令。
4. 更新 `agent-trace-view/web/*`：节点 ID、双模式、展开折叠。
5. 可选：更新 `trace_template.md` 以说明如何实例化已有工作流到目标项目。
