# Q8 · 纠错方案本身可能是"看似正确实则站不住脚"的幻觉，怎么解决？

## 问题（纠正 Q7 的"幻觉"定义）
用户对"幻觉"的准确定义：**agent 提出的纠错方案看似正确、实际站不住脚（错误的修复方案）**——而非工具编造不存在的步骤。即：用户报出入后，我给的修复理论可能是错的，怎么防？

## 回答
这是元层级风险：agent 用自己的（可能错的）推理去修自己的错。解法是**不让方案靠"被断言"成立，而靠"被证伪/被独立验证"成立**，且**警惕错误的全局规则比错误的单点更致命**。

### 一、让方案"可被证伪"，而非"被断言"
- **方案须带可检验预测**：提出修复时必须同时给出可观察断言——"打补丁 Y 并重 trace 后，X 将变为正确，且同类节点 Y、Z 会以〔具体可观察方式〕改变"。然后**实际运行并核对预测**；预测失败 → 方案**拒收**（不静默应用），重新理论化。
- **先复现，再理论**：提出任何方案前，必须先以当前图 / trace **复现**用户报的出入。复现不了 = 方案建在沙上，直接拒收并追问细节。顺序是：复现 → 定因 → 出方案 → 验预测。凭空编的"合理故事"被流程挡在门外。

### 二、方案不由提出者自证（独立验证 + 人确认）
- **非 LLM 校验**：补丁 + 重跑后，图是否在 X 点匹配用户真值？是、且用户确认，才收。验证器不依赖提出方案的同一推理链。
- **用户即真值源**：方案作为"假设 + 证据"交用户确认，agent **不自证其修**；只有用户确认才闭合 correction。
- **对抗式自否**：动手前显式尝试*证伪*自身理论——"什么证据能推翻我的判断？我找得到吗？"若找不到反证但理论并不平凡，标 `pending-user-confirm` 而非 `resolved`，不抢答"已修好"。

### 三、防"错误的全局规则"比"错误的单点"更危险
- **不确定根因时，偏局部有界修正**：改 X + 圈定其 provenance 同类节点待审，而非基于可能错的理论去改**全局捕获规则**（Q7 的"修机器"若理论错，会污染整图，比错改一个节点更糟）。
- **全局规则须由已验证局部证据"赚得"**：仅当局部修正被重 trace 证真、且同机制被确认确致 Y、Z，才把局部提升为全局规则。全局规则来自已验证的局部，不来自动人的故事。
- **纠错留痕可重开**：每条 correction 记"方案 + 可检验预测 + 重跑结果 + 用户确认"；后续若同区再被推翻，框架浮现该记录。从不声称"最终修复"，只声称"据此证据已修，可被反证重开"。

### 需确认的点
- 是否强制"方案不带可检验预测就不允许写入 correction"？倾向强制——从流程上堵死空泛修复。
- 全局规则提升为默认需几例已验证局部？倾向 ≥2 例同类（防单一巧合误导）。
