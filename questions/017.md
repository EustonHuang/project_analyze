# 问题：project_analyze_flow.json 的设计思路与潜在问题

## 问
这份 trace JSON 的设计思路是什么？有没有潜在问题？潜在问题是什么？

## 设计思路（意图）
- 这是一份「项目本体解剖」trace，把 architecture/003 的 Agent 工作流在 project_analyze 上实例化。
- 顶层 `phases` 把流程切成顺序阶段；每个 phase 用 `kind` 声明执行语义（parallel / sequence）。
- 每个 node 是一个步骤，`source` 把步骤锚定到真实代码/配置行（可溯源）。
- `children` = 流程里的「下一步」（顺序 sibling）；`yes_branch` / `no_branch` = 决策分支。
- `conditions` / `assumptions` 单独记录决策点与前提。
- 意图：轻量、代码可追溯的工作流模型。

## 潜在问题
1. **`children` 字段名暗示「父子层级」，实际是「顺序下一步」**——命名误导，正是之前 expand/collapse 误会的根因。应改名 `next` / `flow`。
2. **阶段衔接是隐式的**：P2 末节点 `children` 指向 P3 首节点，没有显式「阶段顺序边」。某阶段末节点漏指，图会静默断裂；也无法校验阶段是否连成一条链。
3. **节点 `id` 命名混乱**：`s1/n1/n10` 混用类型前缀且编号不连续，暗示不存在的结构，无规范约束。
4. **阶段不是一等公民**：`phases` 只是分组元数据，viewer 要自己重建阶段容器，「阶段」概念二等化。
5. **`conditions` 与 decision 节点的 question 重复存储且无显式关联**，易漂移。
6. **`kind` 取值未受约束**（代码里出现 entry/step/decision/exit/io/parallel/loop/trigger/branch/async/spawn…），trace 只用子集，缺 schema 校验易写错。
7. **并行 sibling 在节点层面无标记**，脱离 phase 上下文就丢失「并行」信息。
8. **决策分支与顺序都用节点引用，图里会出现环**（n16→n12/n14），模型没有显式 loop 构造，难区分「有意循环」与「面条图」。
9. **`source` 大量重复**（节点、phase 都带），文件移动需多处改。
10. 只有 meta 级 `standard_version`，**节点级 schema 无版本**。

## 最该先修的
(1) `children` 改名；(2) 显式阶段顺序边 + 连通性校验；(3) 节点 id 规范。
