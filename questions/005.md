# Q5 · 当剖析出的 workflow 与实际不符时，如何保住可信度？

## 问题
如果 agent 反应出的 workflow 和真实 workflow 有出入，只要有一次出入，整个 workflow 的可信度就大打折扣。怎么处理这个问题？

## 回答
前提：无法承诺"零偏差"（尤其 Mode A 概念/agent 流本质是推断）。正确做法是**让偏差可见、可溯源，且绝不把推断伪装成事实**——可信度来自"诚实 + 可验证"，不来自"声称完美"。落到 `questions/001.md` 的模型上，五条机制：

### 一、根因：两种 capture 可信度本质不同（先分层）
- **Mode B 代码追踪**：用真实执行 trace 时为**事实**（高可信）；仅靠静态调用图推断时为**不完整**（低可信）。
- **Mode A 概念/agent 流**：本就是 agent 对触发链的**推断**（天然易出入）。
- 铁律：推断绝不能以"事实"面目出现——必须显式标注所属层级。

### 二、每个节点带"来源凭证 + 置信度"
- node.meta 存证据：代码模式存 `file:line` + 实际 trace 片段；概念模式存定义出处（如某 skill 的指令文件、某 hook 的 settings.json）。
- node.confidence ∈ {`traced` 已追踪, `modeled` 推断, `unverified` 未验证}。
- viewer 对每节点显示徽章；提供「只看已验证(verified-only)」过滤——筛出保底可信的核心 workflow，其余灰显/折叠。

### 三、代码模式：用真实执行 trace 代替推断
- 优先动态插桩（`sys.settrace` / `cProfile` / 真实跑一次），让图 = **实际那次运行**，而非猜。
- 静态调用图仅作兜底，且整张子图打 `static/incomplete` 标，不混入 traced 区域冒充事实。

### 四、验证闭环（自动 + 人工纠错）
- **复跑 diff**：同一输入跑两次，trace 不一致 → 标记该区为「非确定」，不假装确定。
- **交叉校验**：代码 `call` 目标须存在于源码；agent `触发` 节点须对应仓库真实 hook/skill/memory 定义；不可验证 → 发 warning 并置 `unverified`。
- **纠错留痕**：用户发现出入 → 追一条 correction（仿本框架 append-only），图修订且保留 provenance，绝不静默涂改。

### 五、非确定性的诚实表达
- 异步/并行/agentic 循环的顺序本不固定：渲染「本次观察到的所有路径」，或把边标为 `observed-this-run` / `possible`，**不编一条单一线性顺序**冒充真实。

### 需确认的点
- 对外暴露哪几档置信度徽章？建议仅 `traced / modeled / unverified` 三档（不细分，避免用户决策疲劳）。
- 「未验证」子图是**阻止发布**还是**照常发布但灰显标注**？倾向后者（保留信息量，靠徽章+过滤保可信）。
