# Q7 · 纠错透明下，如何解决"头痛医头"与"幻觉"？

## 问题（承接 Q6「纠错透明」）
1. **头痛医头 / 打地鼠**：用户报 X 错 → 只修 X，但同一根因还在 Y、Z 悄悄出错，永远在补单个节点。怎么治根因？
2. **幻觉**：agent 编出根本不存在的步骤/边（尤其 Mode A 概念流，或渲染器/追踪器误标）。怎么解决？

## 回答
两类问题的共同解法是：**修的是"造图的机器（捕获/校验规则）"，不是"图里的点"**；幻觉则靠"无证据不出节点"从结构上禁止。

### 一、头痛医头：治"根因"而非"节点"
- **缺陷分诊（归小类）**：每个纠错不急着改节点，先归入少量**缺陷类**——如「捕获规则误触发」「静态分析漏了动态分发」「无证据推断」「渲染器错位」。被修的是"类"，不是"点"。
- **规则补丁 + 全图重跑**：定位缺陷类后，修的是**捕获/校验规则**（如"追踪 asyncio 时也要插桩 TaskGroup"），然后**重跑整个项目**或按新规则**重验已有图**。Y、Z 属同类，一次过修正——这是修机器，不是修图。
- **provenance 爆裂半径 + 缺陷类登记**：节点带"由哪条规则/哪步推断生成"。某规则被发现有误，可枚举全图**所有**由它生成的节点，一次性圈定重验（有界爆裂半径，非无限逐点）。另设**缺陷类登记册**：新纠错先比对册子，若是已知类说明规则仍不足、要补强；避免反复重新发现同一类。

### 二、幻觉：结构性杜绝"无证据不出节点"
- **证据绑定硬规则**：节点/边**必须**挂具体证据 token（trace 行 / `source file:line` / 仓库真实 hook·skill·memory 定义），否则进 `unverified`/隔离区，**绝不**以事实面目进图。幻觉的本质就是"无证据也出节点"——从生成结构上禁止。
- **Mode A 显式"假设"而非"事实"**：推断节点一律标 `modeled`/`unverified`，用户本就打折；即便某 Mode A 节点是编的，也无法伪装成"已观测"，危险被标签制消解。
- **生成 / 验证分离 + 独立真值**：LLM 只出**候选**，由**非 LLM 验证器**（基于 trace / 源码 / 仓库真实定义）只放行有证据者——标准"生成器+判别器"抗幻架构。对 agent 流，每个声称的触发都去 `.codebuddy/settings.json`、`skills/`、`memory` 真值比对；编出的 skill 触发因仓库里查无此物被丢弃/标红。Mode B 下重跑确定性检查：幻觉节点不在 trace 里，重 trace 即消失。

### 三、并入同一条"根因闭环"
- **元原则：偏"重推导"而非"手改"**：受影响的子图用**修正后的规则从源/重 trace 重新生成**，而非手工编辑节点。手改是打地鼠，重推导是治根。
- **主动展示而非藏**：交付「已知局限清单」+ 缺陷类回归集，让用户看到"这类我已识别并在修"，反增可信。

### 需确认的点
- 缺陷类是否固定为 4 档（捕获误触发 / 静态漏动态 / 无证据推断 / 渲染错位）？还是随实践扩展？倾向先固定 4 档、后续可加。
- "无证据节点"是默认进 `unverified` 灰显，还是直接不渲染？倾向 `unverified` 灰显保留信息量（与 Q5/Q6 一致）。
