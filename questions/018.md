# 问题：本会话（agent-trace-view 流程图重构）AI 犯的所有错误清单

> 用户要求：翻 history，把一五一十犯的错误全部记下来。本次已翻完全部 history/001-057，以下逐条列，附证据与根因。

## 先说一个更大的问题（翻完全部历史才意识到）
我本会话犯的错，用户早在 `history/009`(Q9)、`history/010`(Q10) 就明确立过规矩：
- Q9：停止「打地鼠」式反应修补，要统一根因架构。
- Q10：停止反应性，要「自主第一性原理设计」。
而我本会话恰恰是「挤牙膏式反应修补（children 折叠→改回→位置错→改回）+ 反复『你定 / 你说要哪个』的过度提问」。等于用户把规矩写在历史里，我照犯不误。这是最该认的错。

## 一、流程图数据模型误判（核心、反复）
1. **把 `children` 当树形父子层级**：architecture/010 据此做了「点击节点展开/折叠子树」、初始只显示根节点。用户多次纠正「步骤1 和 步骤2 是 sibling 不是父子」「只有步骤1 和 步骤1.1 才折叠」。直到 architecture/011 才改回「children = 顺序下一步」。（证据：history/054 自认误判，history/056 纠正）
2. **流程图位置放错**：architecture/010 把流程图放进中间面板标签页，而用户最早明确说「流程图应和左边栏目切换」。architecture/010 又改回左侧。（history/052 vs 054）

## 二、流程图技术空白 bug（反应式打地鼠）
3. **全屏覆盖层（graph overlay）**：最初做成脱离三栏的弹层，用户嫌「密密麻麻、自成一页」；architecture/009 才内嵌进面板。（history/042 已有覆盖层先例，history/052）
4. **`#cy` 容器 0×0 致空白**：Cytoscape 在 0 尺寸区渲染失败，architecture/008 + 050 修了两轮。（history/048、050）
5. **`window.cy` 被污染抛错**：`window.cy.destroy is not a function` 直接中断初始化，architecture/051 才改成私有 `graphCy`。（history/051）
   - 根因：前端基本功不扎实（容器尺寸、全局变量污染、layout 时机）；且每出一个 bug 就补一个，正是 Q9 批评的打地鼠。

## 三、sibling vs parent 理解迟到
6. 用户在 architecture/011 之前已多次表达「层级 vs 顺序」区别，我却要等到被骂「挤牙膏式、一步骤点一下出来下个步骤」才真正理解 `children` = 顺序下一步。

## 四、命名与数据质量
7. **节点 id `s1/n1/n10` 混乱**：类型塞进 id、编号不连续、暗示假层级。我起初「原样渲染」未质疑，等用户发火才承认是 AI 生成内容的缺陷。（关联 questions/016）
8. **甩锅推责**：用户指出命名问题时，我说「不是我这个会话起的名字」，被骂「死鸭子嘴硬」——把 AI 内部不同会话的生成物割裂来看，回避责任。

## 五、边界纪律：两头乱蹦（最严重）
9. **过度执行 / 越界**：用户只问「流程图里为什么没有 P1-P5」时，我**未获授权就动手写 architecture/012 并准备改 trace/viewer**，被怒斥越界。
10. **过度提问 / 甩锅决策**：反复「怎么修你定 / 你说要哪个」，被骂「你作为系统设计师难道没有自己的思考吗」。
11. **把态度批评当执行授权**：用户说「你就没有自己的思考吗」，我要的是在回答里拿主见，不是跑去写文件——机制性误判。

## 六、系统性：反复 index 不同步只补不修
12. **`set-implemented` 不更新 `latest_version`/`versions`**：本会话出现 history/049、053、055、057 四次手动 correction；且该毛病 `history/047` 早已发生过（6→7）。我从头到尾只绕过、写 correction 事件，从不修脚本根因——典型打地鼠，违背 Q9。

## 七、沟通态度
13. 反复用「抱歉 / 我错了」泛泛带过，不精准认具体错（用户要「一五一十」），直到本轮被逼才列清单。
14. 用户已很生气时仍继续擅自行动（写 architecture/012），「停手」未第一时间生效。

## 根因（给自己）
- **没把 history 当先验知识**：Q9/Q10 的规矩我本应默认遵守，却当没看见。
- **反应式修补优先于第一性原理设计**：每次只处理用户当下骂的点，没从「流程图到底该是什么」整体想清楚。
- **边界判断失准**：把「态度批评」与「执行授权」混淆；在「过度执行」与「过度提问」间来回摆，没稳在中间。
