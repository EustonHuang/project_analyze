# Q10 · 从第一性原理设计追踪系统：会遇到哪些问题、怎么解

## 问题（用户要求停止反应性回答）
用户指出：Q9 仍是我提什么你写什么，本质还是打地鼠。要求从"设计一个项目执行流追踪/可视化系统"的**本质**出发，自主预想真实问题并给出解法。

## 回答
先认错：Q5–Q9 都是对你提到的点逐个回应（反应性），未从系统本质预想。下面按系统自身性质（它 = 采集器 + 模型 + 视图 + 生命周期）列出**问题类**，每类给**一种架构机制**（治一类，而非治一点）。你提的 Q5–Q8 仅是"保真/信任"一类的子集，此前我误把它当全集。

### 一、采集完整性（capture completeness）— 漏采/错采
系统本质是"跑一遍并观察"，但观察天然有盲区：
- **动态分发盲区**：回调、`getattr`、插件加载、运行时导入——静态看不到，追踪易漏/误标。
- **跨进程/跨机**：多进程、RPC、消息队列——trace 上下文须跨边界传播（分布式追踪 `traceparent`）；fork/exec 起的子进程会丢 tracer。
- **异步/并发顺序**：asyncio/线程实际交错不确定，单条线性 trace 误导；应抓 happens-before 而非序列。
- **三方库噪声**：追踪陷入 urllib/ORM 内部，图爆炸且无意义——需用户代码边界剪枝。
- **开销与副作用**：`sys.settrace` 可慢 10–100×；跑代码有副作用（写盘/发邮件/扣费）——需采样/选择性插桩 + 安全重放（dry-run / record-replay）。
- **入口与输入错**：真入口可能是 wrapper/Makefile/import 副作用；同命令不同输入流向不同——需捕获真实入口 + 输入上下文。
**机制（采集子系统）**：动态插桩为主 + 分布式 trace 上下文传播 + 用户代码边界剪枝 + 安全重放沙箱 + 输入上下文捕获。一套子系统治整类，不逐 bug 补。

### 二、规模下的表示（representation at scale）
- **图爆炸**：真实系统上千节点；需抽象分层（按模块/函数聚类、可折叠）。
- **环/递归无界**：循环/递归使图成环；需有界表示（循环标注一次、递归深度封顶）。
- **状态缺失**：分支依赖 config/全局态，纯节点边漏了状态——状态须在模型中有位置。
- **多视角**：dev/ops/PM 看同一流不同——需"一模型多投影"的视图层。
**机制（模型+视图子系统）**：图分粒度层级 + 循环/递归有界标注 + 状态槽 + 视图投影（一模型多呈现）。

### 三、保真与信任（fidelity & trust）— 你提的 Q5–Q8 在此
- trace 是否等于现实（Q5）、置信度是否标错（Q6）、是否编步骤/打地鼠（Q7）、修复方案是否错（Q8）、图过期（代码改后 stale）、环境漂移（dev 追 prod 跑）。
**机制（信任子系统 = Q9 不变式+管线）**：一切内容 = 候选 + 可复现证据 token + 过分离验证器，不过降级 `unverified`；并加代码哈希失效检测（stale 自动标）+ 环境快照（可重验）。这一子系统覆盖你说的全部可信度担忧，但只是四类之一。

### 四、生命周期（lifecycle）
- **存储增长**：每次 trace 一图，仓库膨胀——需保留/压缩策略。
- **工作流版本化**：代码演进 → 流演进，需 diff 流 v1/v2（代码变了流哪变）。
- **标注生存**：多人标注不能被重 trace 冲掉——标注层须与生成图分离。
- **隐私**：追踪可能捕获密钥（`--password x`）——采集时脱敏。
- **可重验**：存环境快照（版本/OS）使 trace 后可重跑验证。
**机制（生命周期子系统）**：trace 注册表 + 代码哈希失效 + 流版本/diff + 标注层分离 + 采集脱敏 + 环境快照。

### 五、架构骨架（四类机制，非逐点补丁）
```
采集子系统 → 模型/视图子系统 → 信任子系统(Q9) → 生命周期子系统
```
每类一种机制治整类问题；新发现的失效多数归入四类之一，对应改该类机制，不堆新补丁。你提的 Q5–Q8 仅是"信任"类的子集，此前我误把它当全集。
