# 问题：流程图的完整步骤类型是什么？本项目 trace 有没有覆盖？为什么实现缺斤少两？

## 问
1. 流程图中到底有哪些步骤类型（除开始/终止、条件、输入输出之外，完整集合是什么）？
2. 本项目 `agent_traces/project_analyze_flow.json` 的 trace 方法，有没有覆盖流程图的所用步骤类型？如果没有，为什么？
3. 之前在 questions 里对流程图步骤类型剖析得很完整，为什么真正实现时反而缺斤少两？

## 答

### 一、流程图的完整步骤类型（依据 questions/002 的剖析，ISO 5807 / ANSI）
1. 起止（圆角矩形）
2. 处理 / 步骤（矩形）
3. 判断 / 条件（菱形）
4. 流向线（箭头）
5. 循环（判断 + 回边，或 ISO 专用 loop 符号）
6. 准备 / 初始化（六边形）
7. 预定义处理 / 子程序 / 递归（双边矩形，call）
8. 输入输出（平行四边形）
9. 数据存储（圆柱体）
10. 文档（波浪底矩形）
11. 连接符（小圆）
12. 汇合（多入一出）
13. 并发 / 并行（粗横线 fork–join）

据此收敛出的工具 `kind` 清单（questions/002 第五节）：入口 / 触发 / 调用 / 并行分叉 / 循环 / 分支 / IO / 异步任务 / 进程线程。

### 二、本项目的 trace 实际覆盖了多少？
- **trace 实际用到的 `kind`**（实测 `project_analyze_flow.json`）：仅 `entry`(1)、`step`(15)、`decision`(4)、`exit`(1) —— **4 种**。
- **viewer 的 `SHAPE_BY_KIND` 定义了 11 种**：entry / exit / step / decision / io / parallel / loop / trigger / branch / async / spawn。
- **结论**：设计层（剖析 + viewer schema）与完整类型基本对齐；但**数据层严重缺斤少两**——trace 只 populated 4 种，另外 7 种（io / parallel / loop / trigger / branch / async / spawn）定义好了却一个都没用。

### 三、它起到「完整流程图」效果了吗？
**只起到退化版效果**：能画出「开始 → 步骤 → 判断 → 结束 + 分支」的骨架，但——
- 分不清 I/O 步骤与普通步骤（如 n26「写入 history 事件」、n21「前端渲染展示」本质都是 I/O，却都标记为 `step`）；
- 看不到并行分叉（P1 的 s1/s2/s3 并行，图上与顺序节点长得一样）；
- 看不到环是环（n16→n12 是循环，但只是隐式边，不是 `loop` 节点）。

### 四、为什么剖析头头是道、实现却缺斤少两？（根因）
1. **schema 与 instance 脱节，无校验兜底**：`kind` 清单写在设计（questions/002、architecture/003）与 viewer 样式里，但**没有任何校验强制 trace 用对 kind**。实例化时（更早的 AI 会话）走捷径：所有节点一律填 `step`，结构全靠 `children` / `yes_branch` 表达。
2. **并行 / 循环被降级到「边」和「phase 属性」，没落到节点 kind**：P1 的并行是 `phase.kind=parallel` 这个**阶段级**属性，节点层三个 skill 跟普通 `step` 无区别；循环是分支边隐式形成的，不是 `loop` 节点。那 7 个富类型因此成了**死 schema**。
3. **自己在 questions/002 写了「记时模型精简、展时图形丰富」**：本意是 kind 精简、靠边表达结构；但 trace 作者把这个哲学执行到极端，把 io/parallel/loop/trigger/spawn 全空着，导致「展时图形丰富」那一半直接失效——**设计说了两头，实现只落了一头**。

### 五、修复方向（待 architecture 落地）
- 给 trace 增加校验：每个节点 `kind` 必须落在受控集合，且 I/O、并行、循环等语义必须用对应 `kind` 而非统统 `step`。
- 把阶段级 `parallel` 下沉为节点的 `kind: parallel` 或 `parallel-member` 边；把隐式环显式标记为 `loop`。
- viewer 已支持 11 种 kind，只需数据补齐即可「展时图形丰富」。
